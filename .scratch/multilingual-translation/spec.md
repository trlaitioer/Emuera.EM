# 多语言翻译：代码覆盖层（spec）

> 状态：设计定稿（未实现）
> 特性 slug：`multilingual-translation`
> 目标解释器：Emuera（eraBasic 解释器，`net10.0-windows`）
> 相关文档：`docs/architecture.md`、`docs/agents/domain.md`

---

## 1. 问题

eraBasic 游戏由 `csv/`（数据）与 `erb/`（脚本）构成，**文本是单一语言的**——作者写的是什么语言，游戏就是什么语言。社区想把这类游戏翻成中文/其它语言，但目前**没有任何面向「游戏内容」的多语言机制**：

- 解释器**已有**一套 UI 本地化机制：`Runtime/Utils/EvilMask/Lang.cs`（`[Translate]` 特性 + `[Managed]` 反射收集 + `lang/emuera-*.xml` 覆盖 + `SetLanguage`）。但它**只面向引擎自身的固定文本**（`Lang.UI.MainWindow.*`、`Lang.Error`、`Lang.MessageBox`），键是静态编译期 ID，无法表达「上下文」「出现次数」「歧义」，**不能用来翻译游戏内容**。
- 游戏文本分散在三个层面：
  1. **CSV 数据字段**（如 `*NAME.csv` → `Str1DConstantToken`、`NAME/CALLNAME/NICKNAME`）：结构化的显示名。
  2. **ERB 脚本字面量**（`"..."`=`LiteralStringWord`；`@"..."`=`StrFormWord`）：散落在代码里、与逻辑混在一起的叙述/对话/选项文本。
  3. **运行时计算串**：`STRDATA`/`DATAFORM` 等指令把模板求值成平铺 `string`（`GetStrValue()`），模板结构立即丢失；`STR`/`STRS` 等字符串变量只是朴素 `string[]`，**无法反溯来源模板**。
- **致命难点**：这些字符串不仅是「显示文本」，还会被用作**分支判断、动态 CALL、字符串比较、前缀匹配**。若整体翻译「存储值」，会破坏游戏逻辑。而「含内插的字符串」（如 `%CALLNAME%`）按渲染实例翻译又会按角色爆炸（几百上千条）。

目标：给解释器加**原生多语言翻译**，同时**完全兼容现有游戏脚本**。硬性红线：**原 `.erb`/`.csv` 一字不改**，翻译层完全可选、出错回退原版。

## 2. 定稿方案（v1：代码覆盖层，函数级）

### 一句话概括

**不翻译字符串**，而是通过**旁挂的覆盖文件**（`.erbx`）直接**替换游戏函数**来实现翻译——把负责输出文本/逻辑的函数覆写成译版。原 `.erb` 零改动，完全兼容现有游戏脚本。字符串级翻译作为后续可拓展项，本期不做。

### 2.1 文件形态与装载

- 覆盖文件树：`tl/<language>/` **镜像** `erb/` 目录结构。
- 函数级覆盖文件扩展名 **`.erbx`**（原始 `.erb` 的翻译版）。
- 片段级覆盖（后续）使用**另一种扩展名**，与 `.erbx` 区分（见 §3 被否决/搁置项）。
- `.erbx` 内容为普通 eraBasic，直接 `@FUNCTION_NAME` 定义同名函数来覆盖。

**装载改造点：**
- `Config.getFiles`（`Emuera/Runtime/Config/Config.cs:405`）：放开「扩展名长度 ≤4」过滤，改用显式 `*.erbx` 模式（现在 `.erbx` 长度 5 会被直接丢弃）。
- `ErbLoader.LoadErbDir`（`ErbLoader.cs:44`）之前/同时，新增对 `tl/<语言>/` 树的扫描与加载。`tl/` 是 `erb\` 的兄弟目录（`Program.ErbDir` = `WorkingDir + "erb\\"`，`Program.cs:337/350`），需在 `ErbLoader.cs` 或 `Process.cs:221/250` 范围外增加 gather；
- 参考同类加载器：`.ERH` 走 `ErhLoader.LoadHeaderFiles`（`ErhLoader.cs:36`）；`.erd`/`.csv` 走 `ErhLoader.PrepareERDFileNames`（`ErhLoader.cs:361-380`）。

### 2.2 覆盖机制（函数级，核心）

- **全量替换**：当 `.erbx` 定义了 `@FUNCTION_NAME`，则原 `.erb` 中的同名函数被**完全替换**，其函数体**不再注册/不再解析**（翻译版全权接管）。
- **顺序**：先加载 `.erbx` 覆盖函数的标签，建一张「覆盖表：函数名 → 覆盖标签」。加载 `.erb` 时，凡函数名命中覆盖表 → **跳过该原函数的注册与解析**；未命中 → 照常注册。
- **统一插入点**（关键，已被源码证实）：CALL/跳转解析在 parse-time（`setJumpTo`↔`CALL_Instruction.SetJumpTo`，`Instraction.Child.cs:1292`）与运行时（`Process.CalledFunction.cs:109`）**都走** `GetFunctionMethod`（`IdentifierDictionary.cs:562`）→ `GetNonEventLabel` → `noneventLabelDic[name]`。因此只要让覆盖标签成为 `noneventLabelDic[name]` 的**唯一项**，CALL/跳转就会自动定向到覆盖版。
- 实现要点：现有 `LabelDictionary` 的同名函数处理是「先加载生效」（`SortLabels`，`LabelDictionary.cs:58`，取 `list[0]` 即最小 `FileIndex`）。因此**「`.erbx` 先加载 + 跳过原函数」**即可让 `SortLabels` 自然选中覆盖版，无需改动 Jump 解析核心。

### 2.3 语言选择与持久化

- 新增 `ConfigCode` 键（如 `TranslationLang`），记录当前生效的翻译语言。
- 启动时检测 `tl/<language>/` 是否存在；若存在 → 让用户选择语言；若不存在 → 完全无覆盖、原版运行。
- 所选语言写回配置，下次启动沿用。

### 2.4 兼容与安全红线（不可违背）

- 原 `.erb` / `.csv` **零改动**。
- `.erbx` 缺失 / 为空 / 格式错误 → **整体弃用该文件、回退原版**，绝不让翻译层把游戏搞崩。
- 覆盖引用不存在的函数 → 警告并忽略，不崩溃。
- 覆盖层**完全可选**：不装 `tl/` 就是原版游戏。

### 2.5 配套工具（必带）

- **生成覆盖模板**：扫描 `erb/` 下所有函数名，输出 `.erbx` 骨架（每个函数名一行/一段、标注原函数名），供译者逐个填充翻译版。

### 2.6 本期明确不做（记录，后续再议）

| 项 | 说明 |
|---|---|
| 片段级内容哈希覆盖 | 需新做「按内容哈希改写函数体」层；单条逻辑行/去首尾空白与行尾注释/重复后缀/哈希算法均搁置 |
| 字符串模板层 / 简化翻译 | 等后续有好的方式再拓展 |
| 调用原版逃逸口 | 曾设想 `CALL ORIGINAL:F` / `#DIM` 特殊标记 / 函数作用域暴露特殊名；后续再做 |
| CSV 数据字段翻译 | 数据字段常被用作分支/比较/CALL 目标，整体翻会破坏逻辑；本期不做 |

## 3. 被否决的方案与否决原因

| 方案 | 结论 | 否决原因 |
|---|---|---|
| **复用现有 UI 本地化 `Lang` 机制** | 否决 | `Lang` 是「静态键 + 编译期 ID」：`[Translate]` 特性写在引擎 C# 源码里、反射收集；翻译文件 `lang/emuera-*.xml` 的 `id` 与内容无感知。无法表达「上下文」「出现次数」，无法成键消歧，**只能翻引擎固定文本**。只复用其**外围管线**（`useLanguage`/`LangManager.setEncode` 编码、`GetLangList` 语言枚举、`SetLanguage` 流程、「未覆盖回退原文」思想）。 |
| **数据层替换**（翻译 CSV/常量字符串的存储值） | 否决 | 字段名（如 `ITEMNAME`、性格名、`CDFLAGNAME`、`NAME`）会被**分支判断 / 动态 CALL / 字符串比较 / 前缀匹配**使用，整体翻会破坏逻辑；且某些名词「按字段名开头匹配」时会译不得。 |
| **展示层大字典**（对所有最终展示字符串做输出前替换） | 否决 | ①含插值串 `%CALLNAME%` 按渲染实例翻译会**按角色爆炸**（几百上千条）；②`STRDATA`/`DATAFORM` 算出的成品串**模板已丢失**、字典无法按模板定位；③本质是「最终串字典 + 输出前替换」，**性能与覆盖都很差**。 |
| **字符串模板层**（Ren'py 式：`StrFormTerm` 求值前按作者模板键、按名重排占位符、缓存） | 部分采用、搁置 | 本可作主机制，但与「代码覆盖」并存需两套机制。「重排占位符」能保 JA→ZH 质量，但用户判断「较新游戏的字符串拼接与 PRINT 系差别不大」，因此**本期先做纯代码覆盖**，字符串模板层搁置（等后续找到好方式再拓展）。 |
| **片段级内容哈希覆盖 一期就做** | 搁置 | 现有命名空间按「名字 + `FileIndex`」去重，**完全没有「按内容哈希替换语句」的概念**，需新做「按内容哈希改写函数体」层（在 `nestCheck`/`setJumpTo` 之前替换指令链），是一次不小的解释器手术。先做函数级覆盖验证价值。 |
| **调用原版逃逸口** | 搁置 | 一期做全量替换即可；调用原版接口（`#DIM` 或函数作用域特殊名）后续再加。 |
| **hash 截断到 ≤16 hex** | 否决（本期限整体搁置） | 这是**代码覆盖**，碰撞后果（覆盖错代码）比字符串翻译重得多；但本期先不做片段级，且片段级有「函数名前缀」限定，单函数内短代码（`IF`/`THEN` 等）才可能碰撞且翻译一般不改。**先搁置，做完函数级覆盖再重估。** |
| **用行号作翻译键** | 否决 | 行号极脆弱，原文件一改就大量失效；应改用内容哈希（对文本改动稳健、对行号移动稳健）。 |
| **自动改写/修改源文件**（破坏性） | 否决 | 违反「兼容现有游戏脚本」红线；翻译必须纯旁挂覆盖、原文件一字不改。 |

## 4. 影响范围

### 4.1 需要改动的文件（改造点清单）

| 文件 | 改动 | 风险 |
|---|---|---|
| `Emuera/Runtime/Config/Config.cs:405` | 放开「扩展名长度 ≤4」过滤，支持 `*.erbx` | 低 |
| `Emuera/Runtime/Config/ConfigCode.cs` | 新增 `TranslationLang` 配置键 | 低 |
| `Emuera/Runtime/Config/ConfigData.cs` | `TranslationLang` 默认值/访问器（默认空 = 禁用） | 低 |
| `Emuera/Runtime/Script/Loader/ErbLoader.cs:44/344` | 新增 `tl/<语言>/` 树扫描、`.erbx` 函数加载、`.erb` 加载时跳过被覆盖函数 | 中 |
| `Emuera/Runtime/Script/Data/LabelDictionary.cs:58` | 覆盖表构建；`SortLabels` 后让覆盖标签成为唯一项 | 中 |
| 新增 `Emuera/Runtime/.../Translation.cs`（或类似） | 覆盖表、语言选择、生成模板命令、`.erbx` 校验与回退逻辑 | 中 |
| `Emuera/Program.cs` 启动流程 | 语言选择、装载覆盖文件 | 低 |

### 4.2 兼容性影响面

- **对现有游戏**：`tl/` 目录不存在 → **零影响**，完全按原版运行。只需旁挂 `tl/<language>/*.erbx` 才会生效。
- **对原 `.erb`/`.csv`**：完全不变。
- 风险缓解：任何 `.erbx` 的语法错误 / 引用不存在的函数 / 空文件，一律**回退原版**，不影响游戏启动。

### 4.3 性能影响

- 覆盖表在**装载期**构建（一次）。
- 被覆盖的函数**完全不解析**，节省 parse 时间（且避免原函数潜在问题）。
- 运行期无额外开销（CALL/跳转走原有 `noneventLabelDic` 查找，只是键指向覆盖标签）。

### 4.4 不涉及的范围（边界）

- 不改动翻译器的词法/句法/求值核心（除上述装载与 label 定向）。
- 不处理 CSV 数据字段翻译。
- 不做字符串模板层。
- 不做片段级覆盖、逃逸口、hash 算法落地。

### 4.5 安全与数据风险

- 翻译覆盖层是**旁挂**，不会写入或改动任何游戏源文件。
- 唯一需要小心的是 `.erbx` 语法校验与回退逻辑，确保「翻译文件损坏 → 回退原版而非崩溃」。

## 5. 后续 / 未决项（完整设计备忘，切换会话请保留）

> 本期 v1 只做「**函数级代码覆盖**」。以下各项都在设计讨论中深入确认过，因**范围控制 / 风险 / 价值权衡**而搁置到后续。其中「已确认的细节」是**讨论结论**（应保留），「待定的点」是**尚未拍板的开放项**。切换会话时不要把已确认的内容丢掉。

### 5.1 片段级内容哈希覆盖（snippet-level override）

- **概述**：能精准改「某一条调用 / 赋值 / 输出」而不动整个函数，是「代码覆盖」更高一层的形态；用于只改局部而不用整函数重写。
- **已确认的细节**：
  1. 与函数级覆盖**拆分到不同后缀名文件**（`.erbx` 之外的另一种扩展名）。
  2. 片段单位 = **单条逻辑行**（`LogicalLineParser` 切出的最小执行单元）。
  3. 哈希对象 = **去除首尾空白 + 去除行尾注释之后的**行文本（对缩进 / 注释稳健）。
  4. 同一函数内「内容相同」的重复逻辑行 → 用**出现顺序后缀 `_1` / `_2`** 区分（不与相同原文合并）。
  5. 覆盖体形成后**拼进原函数、替换原代码**（作为函数体一部分，而非可独立 CALL 的函数）。
  6. 覆盖标签名 `@__FUNCNAME_<hash>` **合法**：函数名允许 `_` / 字母 / 数字（`IdentifierDictionary.cs:24-31,204`），整个标识符会被当作一个 `IdentifierWord` 读入、不报错。
- **需要新做的解释器能力**：
  - 现有命名空间按「名字 + `FileIndex`」去重，**没有「按内容哈希」概念**；要新做「按内容哈希改写函数体」层——在 `nestCheck` / `setJumpTo`（`ErbLoader.cs:938 / 1485`）之前，对每个 `FunctionLabelLine` 的指令链按哈希逐条匹配、替换成覆盖体。这是一次不小的解释器手术。
- **待定的点**：
  - **hash 算法与截断长度**：讨论中推荐 sha256（或同类快速安全哈希）截断到 **≥32 hex（128bit）**、或直接用完整 64 hex；**不要砍到 16**。但用户观点：有「函数名前缀」作限定，单函数内 16bit 碰撞概率没那么高，只有 `IF` / `ELSE` / `THEN` 等极短代码才可能碰撞、而翻译一般不改这些。**结论：先搁置，做完函数级覆盖再重估。**
  - 哈希算**「原始源码行」**还是**「引擎解析后逻辑行」**（宏展开 / `_Rename` 前后）：推荐算【**原始源码行（读入那一瞬、宏展开前）+ 去空白**】，让译者「照抄即可得 hash」，并由生成工具显示每行 hash。

### 5.2 字符串模板层 / 简化翻译（Ren'py 式）

- **概述**：翻译**作者级模板**而非最终渲染串；能批量、低门槛翻译，并支持占位符重排（JA 主宾谓 → ZH 主谓宾）。
- **已确认的细节**：
  1. 拦截点 = **`StrFormTerm` 求值前**（`Term.cs:112` 的 `.StrForm`，含 `strs[]/terms[]`），且必须在 `StrForm.Restructure`（常量折叠，`StrForm.cs:172-203`）与 `GetStrValue()` 求值**之前**；一旦展平成 `string`（打印 / 写入变量）模板即丢失，字符串变量（`string[]`，`VariableData.cs:23-30`）无来源元数据、无法反溯。
  2. 翻译单位 = **作者模板**（含占位符的 `@"..."` 或纯 `"..."`），一个模板一个键；**按模板缓存**（Ren'py `_translations` dict 思想），避免按渲染实例爆炸。
  3. 占位符**按名**引用、可**乱序**（这是 JA→ZH 质量过关的关键）；命名用「源码写法规范化名」：`%CALLNAME%`→`CALLNAME`、`%TARGET.NAME%`→`TARGET.NAME`、三连符号 `+++`/`***`/`===`/`///`/`$$$`、`%ITEMNAME:x%` 统一归一。
  4. 普通 `"..."`（`LiteralStringWord`，无内插）最简单安全；`@"..."`（`StrFormWord`）最难——只能改字面段、绝不能动 `%` / `{}` / `\@\@` 定界符与占位表达式（否则 `NotFoundCorresponding`）。
  5. 对齐宽度按所选语言字节算（`LangManager.GetStrlenLang`），译文变长会影响 `%var%` / `{var}` 对齐。
- **与代码覆盖的关系（用户决策）**：
  - 用户判断「较新游戏的字符串拼接与 PRINT 系差别不大」，因此**本期先做纯代码覆盖**，字符串模板层搁置、作为后续可拓展项（不彻底否决）。
  - 可选边界（提出但未最终拍板）：模板层只处理「**未被覆盖的函数**」里的模板；一个函数一旦被覆盖，内部字符串全交给覆盖版，模板层不再管。

### 5.3 调用原版逃逸口

- **概述**：让覆盖体能**调用「未被覆盖的原函数本体」**，从而做「局部包装 / 追加改动」而非整段重写；原文更新时只需补差异。
- **已确认**：v1 先做**全量替换**（原函数不被注册 / 不解析）；逃逸口后续再加。
- **备选实现（未拍板）**：
  1. `CALL ORIGINAL:F` 之类特殊语法；
  2. `#DIM` 特殊标记（复用原解析逻辑）；
  3. 在函数作用域直接暴露一个特殊名称。

### 5.4 CSV 数据字段翻译

- **概述**：`*NAME.csv`、`ITEMNAME`、性格名、`CDFLAGNAME`、角色 `NAME/CALLNAME/NICKNAME` 等数据字段，既有显示名、又被用作分支 / 比较 / 动态 CALL。
- **已确认**：本期不做（二期再说）。
- **选项与推荐**：
  - A. 完全不翻数据字段（最安全）；
  - B. **按列标记「纯显示列」**、只翻渲染路径（推荐作为二期方案，避免破坏逻辑）；
  - C. 做「一致性翻译」（显示与所有比较/分支/CALL 侧全局一致）——最复杂、最危险，不建议。
- 推荐：A 起步 + 预留 B；**不做 C**。

### 5.5 需校验的技术疑点（尚未验证，应保留）

- **`*#*` 目录顺序**：`*#*` 命名的目录**先加载**（`FileIndex` 更小）。需确认「先加载 `.erbx` 使覆盖版成为 `list[0]`」是否受此顺序影响——覆盖加载顺序与 `*#*` 先加载是否冲突、需要何种顺序保证。
- **覆盖作用域**：`.erbx` 中的 `@FUNCTION` 是**按名字全局**覆盖（无论原函数在哪个 `.erb` 定义），还是**按镜像路径限定到对应 `.erb` 文件**（讨论中提到用镜像树组织，但「按名全局」vs「按文件限定」未最终拍板）。

### 5.6 一个重要的已确认权衡（保留以免误踩）

- 翻译单元语义：**只翻「展示路径」，绝不进「计算 / 存储 / 比较」路径**，才能避免破坏逻辑。字符串可被存储 / 比较 / 动态 CALL 复用，因此字符串级翻译只能作用于「即将被显示」的模板；数据字段翻译另论（见 5.4）。
