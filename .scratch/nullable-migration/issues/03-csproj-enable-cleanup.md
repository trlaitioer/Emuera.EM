## 方案

### 1. 生成文件 `RikaichanAutogenerated.cs` 的 3 条 CS8618(已按 SKILL 方法落地)

按 SKILL「Common Pitfalls / Generated code produces warnings」的机制,在该文件首行加 `// <auto-generated/>`,由 Roslyn 把生成文件排除在可空分析之外。该文件此前无此标记,故翻转后会被纳入分析并报 CS8618(`from`/`to`/`deinflectRuleData`)。

选此而非另两条的依据:文件由 `Rikaichan.Autogenerate()` 生成,而它读取的 `RikaichanAutogenerated.template.cs` 不在仓库内(磁盘与 git 历史均无),产物无法从仓库再生,「改模板」不可用;`NoWarn` 或 csproj 排除要为单文件破例,不如标记本身直接表达「这是生成代码」。

实测(`-p:Nullable=enable`):`Debug-NAudio` 与 `Debug`(WMP)两配置的 CS86xx 均由该文件的 3 条归零。

### 2. 清 `Emuera.Tests` 的 15 条(见上表)

按契约归属择一处理:

| 归属 | 位置 | 处置 |
| --- | --- | --- |
| issues/07 | `LexicalAnalyzerTests.cs` 的 `*.Words.Collection` | 签名已可空,补判空或 `!` |
| issues/07 | `LogicalLineParserTests.cs` 承接 `ParseLine → LogicalLine?` 的局部 | 局部改可空并补判空 |
| issues/08 | `TestBootstrapTests.cs` 解引用 `ReduceExpressionTerm` 的结果 | 签名已可空,补判空 |
| issues/10 | `ConstantDataTests.cs` 的 `GetCharacterTemplate*.Name` | 签名已可空,补判空 |
| issues/06 | `LogicalLineParserTests.cs` 向 `ParseLabelLine` 传 null 的 console | 签名保持非空,用 `null!` 表达「该路径不使用」 |
| issues/06 | `TestBootstrap.cs` 的 `new ExpressionMediator(null, …, null)` | 同上 |
| issues/11 | `TestBootstrap.cs` 的 `new Process(null)` | 同上 |

### 3. 翻转项目配置
