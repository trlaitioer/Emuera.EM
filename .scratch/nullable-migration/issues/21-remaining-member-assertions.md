# Nullable:其余成员与局部非空断言的复核

Status: ready-for-agent

## 任务

issues/13 的剩余构成中，`null!`（384）、`Argument` 可选字段（83）、`list[i]!`（79）、`(x as T)!`（51）、`JumpTo` 族（40）合计 637 处已由 issues/14 的复核对象 1/2/5/6/7 覆盖；余下的**「其他成员/局部 `!`」（issues/13 记为 401 处）**不在其中任何一条里，占剩余断言的约 39%。本票承接 issues/14 新增的第 8 条复核对象。

这类断言的形态是「接收者本身非空」而非「集合元素非空」，例如对字段、局部变量与容器成员的解引用——可空容器成员的索引（`dict![key]`）、UI 侧集合字段（`escapedParts!`、`radius!`、`nums![i]`）、以及各类成员访问后的再断言。它们没有统一的可空性来源，因此需要先枚举再逐点判定。

## 方案

1. **先出清单**。按 issues/14「口径与清单」的口径枚举本类站点，给出稳定站点 ID（`<文件>#<方法>#<序号>`，不含行号）与接收者类型；排除项写明（成员/属性声明的 `= null!`、`ArgumentListExtensions` 内 2 处、`Emuera.Tests`）。清单入库，作为判定与验收的锚点。
2. **按接收者类型分组判定**，沿用 issues/14 的三类结论（成立 / 不成立但不可达 / 可达缺陷）。同类型接收者共用判据，避免逐点重复推理：
   - 容器字段（`Dictionary`、`List`、数组）：构造点是否保证非空、是否有 `Dispose`/重置路径把它置 null；
   - 局部变量：赋值路径是否覆盖全部读取点；
   - BCL 返回值：该成员是否可空、是否有越界/未命中语义。
3. **可达缺陷不并入本票**，按根因另立票（与 issues/15~20 同法）；不成立但不可达的记入潜在缺陷清单。
4. **保留的断言由 issues/22 补理由注释**，本票只产出判定；冗余断言同票清理。

完成标准：清单内每处给出结论与依据；本类断言在收尾时不存在「未判定」项——这是 issues/14「每处给出结论」能够成立的前提。

## 影响

- 本票是 issues/14 完成标准的必要条件：清单产出前，剩余断言无法声称已逐点复核
- 预计产出若干缺陷票；`Dictionary`/`List` 成员断言如果集中在少数构造点，可能像 issues/13 那样收敛为单点入口，届时在同一票内评估
- 本票不改动 issues/14 已判定的六类断言
