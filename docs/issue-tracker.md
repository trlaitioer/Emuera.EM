# GitHub Issues 使用规范

工作项在 GitHub Issues 中跟踪。贡献者可以使用网页或 GitHub CLI（`gh`），自动化代理默认使用 `gh`。两种入口遵循相同的规则。

## 何时开 Issue

需要讨论行为、等待排期、跨 PR 跟踪进度，或在合并后单独验收时，开 Issue。改动明确、能在一个 PR 内交付并验证时，可以直接提 PR，例如修正一条写错的错误提示。

报告者写清遇到的问题或希望达到的效果即可开票。报告缺陷时，尽量给出复现方法、实际行为和期望行为。即使原因或实现方案尚待调查，也可以提交。

## 范围与拆分

准备实施时，维护者在 Issue 正文写明本次处理范围和完成条件。讨论、复现补充和阶段性验证可以留在评论或 PR 中。范围或完成条件有变时，更新正文。拆出工作时，在原处链接承接票。

| 关系 | 使用条件 |
| --- | --- |
| 父子 | 多项工作共同交付一个需要整体验收的目标时，建立父 Issue（Epic），写明整体目标、范围和完成条件。可以独立验收、排期或交付的工作拆成子票，各自维护进度。同一结果的实现步骤列在票内清单里。 |
| 阻塞 | A 必须等 B 完成才能继续时，将 B 记为 A 的阻塞项。原因不明显时，写清 A 在等 B 提供什么。 |
| 相关 | 两张票共享背景或由同一次排查发现时，互相链接即可。 |

## 状态与关闭

开放的 Issue 按需要使用以下状态标签。

| 标签 | 使用时机 | 摘除时机 |
| --- | --- | --- |
| `status:draft` | 范围或完成条件仍需澄清 | 正文已写清范围和完成条件 |
| `status:need-check` | 实现已交付，仍有单独的验收工作。票中写明待验证的行为 | 验收通过后关闭。需要返工时，摘除标签，保持 Open 并记录待修问题 |

普通待办保持 Open，无需状态标签。PR 写明本次改动、验证方式和关联的 Issue。一张票可以由多个 PR 完成，一个 PR 也可以关联多张票。对每张关联票分别判断是否关闭。

- **部分实现**时，PR 关联 Issue，保留开放状态。
- **完成**时，在 Issue 中给出能核对完成条件的证据，例如包含回归测试和验证结果的 PR 链接。合并即满足全部条件时，可随 PR 合并关闭。仍需手工验收时，由验收者记录结果后关闭。
- **关闭父 Issue** 时，按父票自己的完成条件说明整体验证结果。子票全部关闭后，仍需核对这些条件。
- **决定不做**时，写明原因后关闭。**由其他票取代**时，说明转移的范围并链接承接票后关闭。

## 长期保留的规格与决策

Issue 记录本次范围与验收结果。后续开发仍须遵守的行为和不变量写入 `docs/specs/` 下的 Spec。后续维护者仍需理解的设计取舍写入 `docs/adr/` 下的 ADR，说明做了什么决定、理由和代价。仅涉及单次实现的备选方案可以留在 Issue 或 PR。

## 迁移与引用

日常讨论用 GitHub 实际分配的 `#N` 引用 Issue。从旧 tracker 迁入的票在正文保留完整旧 ID，例如 `原议题：nullable-migration-37` 对应 [#3](https://github.com/trlaitioer/Emuera.EM/issues/3)。历史提交中的 `issues/37` 是主题目录内的编号，查找前应按当时的主题补全旧 ID。

迁入票可按完整旧 ID 搜索，旧票和旧规格的原文见[旧 tracker 归档](legacy-tracker.md)。导入和仓库清理记录见[迁移议题 #2](https://github.com/trlaitioer/Emuera.EM/issues/2)。
